# 模式与框架库

21 个设计模式 + 8 条决策规则 + 11 个反模式。每条都写清"什么时候用"和"什么时候不该用"——后者比前者重要。

## 二、决策规则（if / else）

**R1 要不要拆步骤？**
如果一步之内无法验证对错 → 拆（提示链）。如果每步都能独立验证，也没必要拆到 10 步。

**R2 要不要路由？**
如果同一套流程能处理所有输入 → 不路由。只有当不同输入的"最优路径"明显不同时才路由，且必须留兜底分支。

**R3 要不要并行？**
判据一句话：**B 需不需要 A 的输出**。不需要 → 可并行；需要 → 串行。并行前先算最长分支耗时，收益低于 20% 不值得引入复杂度。

**R4 要不要反思？**
如果拿不出外部判据（测试、原文、清单）→ 不要做反思，那会变成自我感觉。有判据且错误代价高 → 做，上限 2~3 轮。

**R5 要不要拆多智能体？**
先问三个问题：上下文是否装不下？角色是否互相冲突？错误是否无人对照？三个都否 → 单个智能体加更好的提示更划算。

**R6 用 RAG 还是微调？**
知识更新频繁、需要引用来源 → RAG。风格与判断口径要改、知识相对稳定 → 微调。两者不冲突。

**R7 要不要上 MCP？**
固定少量工具（≤3）→ 函数调用。需要跨应用复用、动态发现、多源接入 → MCP。还要先确认底层 API 支持过滤、排序、文本返回。

**R8 要不要插人？**
判据：**错了能不能撤回**。能撤回 → 自动化；不能撤回 → 必须审批，且审批要带上下文。

## 三、11 个反模式

**A1 链条越长越好**
链条的价值是错误局部化，不是步骤数量。每多一环就多一次误差传递与延迟。

**A2 把上一步输出原样传下去**
不裁剪的上下文会稀释注意力。传"需要的那部分",不是全部。

**A3 temperature=0 就以为能复现**
温度只减少采样随机性，不消除框架层的时间戳、检索结果差异、并发顺序差异。

**A4 面具式护栏**
只写"请勿生成有害内容",没有输入校验、工具权限、输出过滤。等于没护栏。

**A5 用另一个 LLM 自由裁量做安全判定**
护栏模型本身也会被提示注入。关键判据用规则、白名单、分类器。

**A6 直接修改 session.state**
绕过事件处理会带来不记录、不持久化、并发冲突、元数据不更新四类问题。走 `output_key` 或 `state_delta`。

**A7 给所有任务打一个"重要性"分数**
忽略依赖出度与就绪状态，会让"被五个任务依赖的小步骤"永远排在后面。

**A8 重试非幂等操作**
超时后重试发邮件、扣款、建单，等于重复执行。重试前必须查状态。

**A9 用 LLM 判优先级**
"ASAP""关键"在模型眼里差不多。优先级要靠结构化字段与规则计算。

**A10 只评最终答案**
结果对但过程违规、结果错但过程合理，两类问题都看不见。要评轨迹。

**A11 无评分函数却做进化式优化**
AlphaEvolve 那类系统的前提是可自动计算的评分。评分写错，进化会朝错误方向狂奔。

## 四、跨模式的三个组合骨架

**骨架 1：产出-检查-兜底**
一个环节负责产出、一个环节按外部判据检查、一个环节在失败时降级或升级。这是最可靠的三人组。

**骨架 2：规划-执行-重规划**
规划给出 DAG，执行按就绪顺序推进，遇到连续失败或约束变化就重规划。适合长流程任务。

**骨架 3：检索-推理-引用**
先检索拿到材料，再推理生成，最后逐条标注来源。适合任何"说错要负责"的输出。
