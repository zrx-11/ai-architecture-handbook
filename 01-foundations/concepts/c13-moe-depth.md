## 🔬 DeepSeekMoE 的第一性原理推导：为什么“专家多、激活少”能同时省算力和涨参数

### 第一步：先看清普通 FFN 的成本

一个 FFN 做两次矩阵乘法：

$$y=W_2\sigma(W_1x)$$

设输入 $d=7168$，中间维度 $m=18432$。参数量：

$$d\times m+m\times d=2\times7168\times18432\approx2.64\ \text{亿}$$

每个 token 都要过这 2.64 亿个参数，计算量也是这个量级。想让模型记住更多知识，最直接的办法是把 $m$ 加大，但每个 token 的计算量跟着涨。

### 第二步：把一个大 FFN 切成很多小专家

把中间维度 18432 切成 256 份，每份 2048 维，每份就是一个“专家”。每个专家的参数量：

$$2\times7168\times2048\approx2935\ \text{万}$$

256 个专家总参数约 75 亿，比原来大 28 倍。但如果每个 token 只激活其中 8 个，计算量是：

$$8\times2935\ \text{万}\approx2.35\ \text{亿}$$

和原来一个 FFN 的 2.64 亿差不多。参数量涨了 28 倍，单 token 计算却没涨。这就是 MoE 的核心账本。

### 第三步：路由怎么选专家

每个专家有一个可学习的向量 $e_i$。token 向量 $x$ 和 $e_i$ 做内积，再取 Sigmoid：

$$s_i=\text{Sigmoid}(x\cdot e_i)$$

Sigmoid 把分数压到 0 到 1 之间。取分数最高的 $k$ 个专家（V3 的 $k=8$），再把这 $k$ 个分数归一化，作为加权系数。每个被选中专家算自己的 FFN，输出按系数加权相加。

### 第四步：为什么还要一个共享专家

路由专家会被不同 token 轮流使用。如果所有 token 都需要“基本语法”这类通用知识，每个被选中的专家都得学一遍，参数浪费。

加一个**共享专家**，所有 token 都过它，专门学通用知识。路由专家就不用重复学通用部分，可以专注细分模式。V3 是 1 个共享 + 256 个路由。

### 第五步：专家为什么会“饿死”

训练初期，某些专家的 $e_i$ 碰巧和很多 token 的内积大，路由把大量 token 送给它们。这些专家梯度多、学得快，变得更强；其他专家拿不到 token，梯度接近 0，永远学不出来。这叫**专家塌缩**。

传统解法是加辅助损失：

$$L_{\text{aux}}=\alpha\sum_i f_i p_i$$

$f_i$ 是分给专家 $i$ 的 token 比例，$p_i$ 是路由概率均值。这个损失惩罚“负载集中”。但它和语言建模目标打架，$\alpha$ 难调。

DeepSeek 的解法：给每个专家一个偏置 $b_i$，路由分数改成 $s_i+b_i$。训练时统计负载，负载高的专家调低 $b_i$，负载低的调高 $b_i$。偏置只影响“选不选”，不影响选中后的加权系数。这样不用往主损失里加项，也能把负载拉平。

### 第六步：一次完整的玩具计算

3 个专家，$k=1$，token 与专家的分数：

- $s_1=0.9$，$s_2=0.5$，$s_3=0.1$

选 top-1 就是专家 1。输出就是专家 1 的 FFN 输出，权重 1。若 $k=2$，选专家 1 和 2，归一化权重：

$$w_1=\frac{0.9}{0.9+0.5}=0.643,\quad w_2=\frac{0.5}{1.4}=0.357$$

输出 $=0.643\cdot\text{FFN}_1(x)+0.357\cdot\text{FFN}_2(x)$。检查：两个权重相加为 1。

### 差生检查

- 参数量与计算量分开算，明确“总参数”和“激活参数”不是一回事。
- 路由、Sigmoid、归一化都给了公式和数字。
- 解释了“共享专家”和“负载均衡”的设计动机，并给了反例（专家塌缩）。
- 玩具计算可以手算复核。
