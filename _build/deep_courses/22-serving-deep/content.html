00课程概览：把模型真正跑起来

训练完的模型只是权重文件。线上服务要处理请求排队、KV cache、批处理、并行、量化、限流和监控。这门课讲清楚一次请求从进来到吐字，钱花在哪。

01一次请求的生命周期

用户发来 prompt，服务端做四件事：

  1. 分词，把文本变成 token id。
  2. prefill：一次前向处理整段 prompt，生成首 token 和 KV cache。
  3. decode：每次前向生成一个 token，把新 token 的 KV 追加到 cache。
  4. detokenize，把 token id 变回文本，流式返回。
阶段计算特征瓶颈
prefill矩阵乘为主，并行度高算力
decode每步只生成一个 token，batch 小显存带宽

首 token 延迟（TTFT）主要看 prefill；每 token 延迟（TPOT）主要看 decode。两个指标要分开报。

“吞吐高”和“延迟低”经常冲突。把 batch 拉大能提高总吞吐，但单条请求要等更久。

02KV cache 与 PagedAttention

自回归生成要缓存历史 token 的 K/V，否则每生成一个 token 都要重算整段历史。KV cache 大小：

$$\text{KV bytes}=2\times \text{seq_len}\times n_{\text{layers}}\times n_{\text{kv-heads}}\times d_{\text{head}}\times \text{bytes\_per\_element}$$

实际实现按模型布局算。以 V3 的 MLA 为例，每 token 每层 576 个数，BF16 下 1152 B；128K、61 层约 9.21 GB。

显存碎片

如果每个请求预分配最大长度的连续显存，短请求会浪费大量空间。PagedAttention 把 KV cache 切成固定大小的块，按需分配，类似操作系统的分页。

好处：碎片少、共享前缀可以复用、并发能开更多。代价：块表管理、注意力 kernel 要支持非连续内存。

PagedAttention 不是“让 KV 变小”，而是“让 KV 的显存利用率变高”。模型本身的缓存公式没变。

03continuous batching

静态 batch：等一批请求齐了，一起跑到结束。短请求被长请求拖住，GPU 空闲。

continuous batching：每步都检查，有请求结束就立刻把新请求插进来。GPU 尽量一直有活干。

方式优点缺点
静态 batch实现简单短请求等待，吞吐低
continuous batching吞吐高，尾部延迟低调度复杂，显存管理难

vLLM、SGLang、TensorRT-LLM 都支持 continuous batching。它不是模型结构，是服务调度策略。

线上常见组合：PagedAttention 管显存 + continuous batching 管调度 + 前缀缓存复用 system prompt。

04张量并行、流水并行与专家并行

单卡装不下时，要把模型切开。三种切法：

并行切什么通信适合
张量并行 TP同一层的权重矩阵每层都要 all-reduce，通信重单机多卡、低延迟
流水并行 PP按层切成多段段间传激活，气泡多跨机、大模型
专家并行 EPMoE 专家分到不同卡路由要 all-to-allMoE 模型

数据并行 DP 是每张卡放一份模型、处理不同 batch，适合模型能单卡装下的情况。

$$\text{总显存}\approx\text{权重}+\text{KV cache}+\text{激活/临时缓冲}$$

MoE 的权重显存按总参数算，激活按 top-k 算；EP 把专家分散，但路由通信变重。

TP 不是越多越好。跨机 TP 的 all-reduce 延迟会吃掉收益；通常 TP 放机内，PP/EP 放机间。

05量化：FP16、FP8、FP4

量化是用更少的位表示权重/激活，省显存、提带宽。代价是精度损失。

精度每数位数相对 FP16 显存典型用途
FP16/BF16161×训练/推理基线
FP880.5×训练、推理加速
FP440.25×推理、边缘部署

量化不只是“把数截断”。需要 scale、zero-point、分组、校准数据。FP8 有 E4M3/E5M2 两种格式，动态范围不同。

量化后精度掉得最多的是长尾 token、罕见词、数学符号。评测要在目标任务上跑，不能只看 perplexity。

06推理引擎怎么选

引擎强项注意
vLLMPagedAttention、continuous batching、生态广新模型支持要看版本
SGLang结构化生成、前缀缓存、调度优化算子覆盖要验证
TensorRT-LLMNVIDIA 平台极致性能编译链复杂，模型转换成本高
llama.cppCPU/边缘、量化格式多高并发不如 GPU 引擎

选型先看模型支持、硬件、并发量、延迟 SLA，再看 benchmark。不要只看社区 star 数。

MoE 模型要确认引擎支持专家并行和路由 kernel；长上下文要确认 PagedAttention 和前缀缓存的实现。

07吞吐、延迟与容量规划

线上容量按三个指标规划：

  • QPS：每秒能处理多少请求。
  • TTFT：首 token 延迟，影响“感觉快不快”。
  • TPOT：每 token 延迟，影响“吐字快不快”。

粗略估算并发

可用显存 = 总显存 - 权重 - 临时缓冲。每请求 KV = 每 token KV × 平均上下文长度。并发上限约：

$$N_{\max}\approx\frac{\text{可用显存}}{\text{每请求 KV}}$$

实际还要留碎片、峰值、调度余量，通常只用到 70%–80%。

按最大上下文给每个请求预留显存，会把并发压得很低。PagedAttention + 按需分配就是为解决这个。

08常见误解与自测

四个误解

  • “batch 越大吞吐越高，所以越大越好”：延迟会炸，显存也不够。
  • “量化一定掉点，不能上线”：目标任务上校准后，FP8 常能保持效果。
  • “PagedAttention 能减少 KV 计算”：它省的是显存碎片，不减少注意力计算。
  • “TP 放在跨机也没关系”：跨机 all-reduce 延迟很高，通常不划算。
