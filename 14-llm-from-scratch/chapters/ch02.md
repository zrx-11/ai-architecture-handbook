# 第 2 章：Tokenizer：把文本变成可训练的数字

- **难度**：★★☆ | **预估学时**：1.5 小时 | **前置**：第 1 章

## 学习目标

1. 手算一次 BPE 合并；
2. 解释词表大小、压缩率、中文 token 成本之间的关系；
3. 写出一个最小 BPE 训练器，并知道它的局限。

## 一句话核心

Tokenizer 不是“分词工具”，它是模型看到的世界边界：词表决定了一个 token 能承载多少信息，也决定了同样的中文要花多少 token。

## 2.1 三种粒度

| 粒度 | 例子 | 优点 | 缺点 |
|---|---|---|---|
| 字符级 | 每个汉字/字母一个 id | 词表小、无 OOV | 序列长、语义弱 |
| 词级 | “人工智能”一个 id | 序列短 | 词表爆炸、罕见词 OOV |
| 子词 BPE | “人工/智能”拆成子词 | 平衡 | 依赖训练语料与规则 |

现代 LLM 多用 byte-level BPE：先以字节为最小单位，再合并高频相邻 pair。这样任何文本都能编码，不会出现真正意义上的 UNK。

## 2.2 BPE 手算

语料：`low lower lowest newer newest`，先按字符切，统计相邻 pair：

```text
l o w   l o w e r   l o w e s t   n e w e r   n e w e s t
```

高频 pair 里 `e s` 出现 2 次，`l o` 出现 3 次。先合并 `l o` → `lo`，语料变成：

```text
lo w   lo w e r   lo w e s t   n e w e r   n e w e s t
```

再统计、再合并，直到达到预设词表大小或没有 pair 可合并。**合并顺序就是词表的一部分**，推理时必须使用训练时保存的同一份 merges。

最小实现：

```python
from collections import Counter

def merge_pair(words, pair):
    out = []
    for w in words:
        i, new = 0, []
        while i < len(w):
            if i < len(w)-1 and (w[i], w[i+1]) == pair:
                new.append(w[i]+w[i+1]); i += 2
            else:
                new.append(w[i]); i += 1
        out.append(new)
    return out
```

这段代码只演示“合并”这一步，不含字节预处理、频率排序、特殊 token 和最大词表截断。真正的 tokenizer 还要处理空格、大小写、Unicode 归一化和聊天模板。

## 2.3 词表大小的取舍

- 词表小：embedding 参数少，但序列变长，注意力成本上升。
- 词表大：序列短，但 embedding 和 softmax 变大，罕见 token 学不充分。
- 中文：一个汉字可能被拆成 1–3 个 byte-level token；词表对中文覆盖差时，同样一句话的 token 数会明显变多。

不要拿“字符数”估算成本。用 tokenizer 实际编码，统计 tokens/字符、tokens/词，再看训练和推理账本。

## 2.4 特殊 token 与聊天模板

至少要有：`<bos>`、`<eos>`、`<pad>`（有的模型不需要）、`<unk>`（byte-level 可不用），以及对话模板的角色标记。模板不是装饰：它决定 SFT 时哪些 token 参与 loss，也决定推理时模型看到的边界。

## 检查点

- 对 `lowest` 从字符开始，手工做 2 次合并，写出每一步语料。
- 用同一段中文分别估算“字符级”和“BPE”的序列长度，说明差异来源。
- 解释为什么推理时不能重新训练一个“看起来一样”的 tokenizer。
