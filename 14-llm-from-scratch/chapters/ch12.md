# 第 12 章：RAG 与 Agent：把模型接到外部世界

- **难度**：★★★ | **预估学时**：2 小时 | **前置**：第 8 章

## 学习目标

1. 画出 RAG 的索引、检索、重排、生成四步；
2. 解释 chunk 大小、混合检索、引用各自解决什么问题；
3. 写一个最小 tool calling 循环，并知道它会在哪里失败。

## 一句话核心

RAG 不是“把文档塞进 prompt”，而是“先检索证据，再让模型基于证据回答”；Agent 不是“更长的 prompt”，而是“模型选择动作、环境返回结果、循环直到停止”。

## 12.1 RAG 四步

```text
文档 → 清洗/切块 → embedding 索引
问题 → 检索 top-k → 重排 → 拼上下文 → 生成带引用
```

- chunk 太小：语义不完整；太大：噪声多、浪费上下文。
- 只做向量检索：对专有名词、数字、代码不敏感；混合 BM25/关键词 + 向量更稳。
- 重排：用 cross-encoder 或 LLM 对候选重排，提升 top-1 命中。
- 引用：让每个结论对应到 chunk id/URL；没有引用就无法审计。

## 12.2 RAG 的失败模式

- 检索没召回：答案再好也无源。
- 召回了但没用：模型忽略证据，凭记忆答。
- 用了错误证据：相似但版本旧/冲突。
- 上下文太长：中间信息被稀释。
- 没有“不知道”：模型硬编答案。

评估要分开测：召回率、命中率、答案忠实度、引用准确率。只看最终答案打分会掩盖检索问题。

## 12.3 Agent 循环

```text
observe → think → choose tool → call tool → observe → ... → final
```

工具调用的最小协议：工具名、参数 JSON Schema、权限、超时、错误返回。模型只负责选择，执行由宿主完成；不要把任意 shell 权限直接交给模型。

## 12.4 常见 Agent 模式

- ReAct：推理与行动交替。
- 计划-执行：先列步骤，再逐步执行。
- 多智能体：角色分工，但通信成本和一致性风险上升。
- 反思：让模型检查自己的结果；没有外部验证时容易“自信地错”。

## 检查点

- 画一条 RAG 数据流，标出至少三个可测指标。
- 解释为什么“向量检索”对版本号/错误码可能不灵。
- 写一个工具调用循环的伪代码，并列出两个权限风险。
